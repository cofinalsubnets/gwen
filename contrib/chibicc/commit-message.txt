Fix parse error on a declarator list whose first declarator is a function

The first example under C89 3.5.4.3, "Function declarators (including
prototypes)", does not compile:

    $ cat t.c
    int f(void), *fip(), (*pfi)();
    $ chibicc -c t.c
    t.c:1: int f(void), *fip(), (*pfi)();
                      ^ expected '{'

Nor does a list built only from prototypes, so this is not about the
non-prototype declarators in that example:

    struct S *f(void), *g(int);
    int a(void), b;

The syntax is C89 -- not a C99 or C11 addition. A declaration carries a
list of declarators, while a function definition takes a single
declarator and so admits no comma (C89 3.5 and 3.7.1, quoted; standing
unchanged in C11 6.7 p1 and 6.9.1 p1 but for C99's removal of implicit
int, which made the specifiers mandatory):

    init-declarator-list:
            init-declarator
            init-declarator-list , init-declarator
    init-declarator:
            declarator
            declarator = initializer
    function-definition:
            declaration-specifiers_opt declarator declaration-list_opt
                    compound-statement

parse() dispatches on is_function(), which inspects only the first
declarator, into function(), which parses that declarator and then
accepts only ';' or '{' -- so it asks whether a declaration begins with a
function declarator, where 3.7.1 needs it to ask whether the declaration
is a definition. Split the symbol-registration half of function() into
declare_function(), hand a comma tail to the existing global_variable()
loop, and have that loop dispatch on ty->kind == TY_FUNC, which also
covers the mixed forms `int f(void), x;` and `int x, f(void);`.

gcc accepts both cases above with zero diagnostics under -pedantic-errors
at -std= c89, c99, c11, c17 and c23; so does clang, but for a
-Wstrict-prototypes complaint about `int *fip()`, which it raises for
that declarator alone with no comma in sight. With the patch, the 3.5.4.3
example compiles and runs correctly -- calling f, dereferencing fip()'s
result and calling through pfi all agree with gcc. Nothing that already
compiled changes: building this tree with and without the patch and
compiling all 49 translation units of the compiler and test/ with each,
the emitted assembly is byte-identical except for parse.c itself and
test/macro.c, whose __TIME__ differs between any two runs a second apart.
make test and make test-stage2 both pass.
